# Story 05 Task 03 Plan: Implement Search Sync Pipeline

## Current State

- Task 02 created `crates/opentk-search` as the production search boundary with pure source-to-index mapping, Meilisearch schema description, API result shape, and storage estimate helpers.
- `crates/opentk-db` owns PostgreSQL connection, migrations, generated table metadata, read models, sync state, and operational binaries.
- PostgreSQL remains the source of truth. The sync pipeline must build `SearchSourceRecord` values from `sync_entity`, generated entity tables, relation tables, `document_asset`, and `document_content`, then map them through `opentk-search`.
- No HTTP search endpoint belongs in this task.
- The selected engine is Meilisearch, but tests must not require a live Meilisearch server. The durable pipeline should be driven through a public index client trait with an in-memory/failing implementation in tests and an HTTP Meilisearch implementation for production wiring.

## Durable State

Extend the existing migration pair with the Task 02 durable tables. Because this is greenfield and there is one current migration, update the existing migration directly instead of adding compatibility migrations.

```sql
CREATE TABLE search_index_cursor (
    index_name text NOT NULL,
    source_category text NOT NULL,
    latest_skiptoken bigint NOT NULL DEFAULT 0,
    last_indexed_at timestamptz,
    state text NOT NULL,
    last_error text,
    PRIMARY KEY (index_name, source_category)
);

CREATE TABLE search_index_failure (
    id bigint GENERATED BY DEFAULT AS IDENTITY NOT NULL,
    index_name text NOT NULL,
    source_category text NOT NULL,
    source_id uuid NOT NULL,
    latest_skiptoken bigint NOT NULL,
    operation text NOT NULL,
    attempt_count integer NOT NULL DEFAULT 1,
    next_retry_at timestamptz NOT NULL,
    error text NOT NULL,
    created_at timestamptz NOT NULL,
    updated_at timestamptz NOT NULL,
    PRIMARY KEY (id),
    UNIQUE (index_name, source_category, source_id, latest_skiptoken, operation)
);
```

Cursor semantics:

- Full reindex resets each selected category cursor to `latest_skiptoken = 0`, state `running`, then advances after each successful index batch.
- Incremental indexing reads changes after the durable category cursor.
- The cursor advances only after the corresponding index client batch succeeds.
- Failed rows/batches write explicit `search_index_failure` records and keep retryable context.

## Source Record Loading

Add a DB adapter that produces `SearchSourceRecord` from PostgreSQL:

- Use `postgres_schema::schema()` to identify entity and relation tables instead of hard-coding generated category tables.
- Reuse read-model style scalar extraction where possible, but avoid forcing search code through HTTP/API DTOs.
- For non-deleted entities, load the entity row, scalar fields, outgoing relations, and incoming relation labels where useful.
- For `Document`, load the selected `document_content` row using the same ordering as `read_model::get_document_content`.
- For deleted entities, produce a `SearchSourceRecord` with metadata only and `deleted = true`; do not require the detail row or document content to exist.
- Relation labels should be resolved from target entity scalar fields using the same title fallback logic as search mapping when possible. If target details are unavailable, use `target_category target_id` explicitly rather than dropping the relation.

## Index Client

Implement the real Meilisearch client by HTTP calls through `reqwest`, keeping request/response DTOs private to `opentk-search`.

Minimum operations:

- `reset_index`: delete the existing index if present, create it with primary key `key`, then apply searchable/displayed/filterable/sortable/ranking settings from `meilisearch_schema()`.
- `apply_batch`: split mixed operations into delete keys and upsert documents, submit to Meilisearch, and wait for task completion.
- Any non-2xx HTTP status, task failure, malformed response, timeout, or JSON error must become a typed `SearchIndexError`.

Do not swallow errors. If any existing helper ignores a failure path, stop and create an add-bug task before continuing.

## Boundary Review

Use `$improve-code-boundaries` before final verification:

- Keep Meilisearch-specific HTTP DTOs private to `opentk-search`.
- Keep PostgreSQL paging, cursor, failure, and source-record loading in `opentk-db`.
- Do not put search sync code in `opentk-api`; Task 04 owns HTTP search endpoint work.
- Do not reuse `opentk-search-eval` DTOs; that crate is experimental benchmark scaffolding.
- Prefer deleting or merging placeholder modules over layering adapters that only rename fields.
- If the DB adapter starts duplicating the existing read model heavily, extract a shared DB-only helper instead of copying conversion logic into two modules.
- If generic schema traversal becomes stringly and opaque, add a small deep module around `SearchSourceLoader` rather than scattering SQL construction across the pipeline.
