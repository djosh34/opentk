# Story 4 Task 1 Plan: Document Content Schema

## Current State

- `opentk-db::postgres_schema` is the PostgreSQL schema boundary. It builds a `SchemaSpec` from `opentk-core::official_schema`, renders the checked-in SQLx migrations, and owns SQL naming, types, indexes, and constraints.
- `Document` currently stores sync metadata, official scalar fields, and `downloadEntiteitType` asset metadata: `content_type`, `content_length`, and `enclosure_url`.
- Existing schema tests verify generated official entity/relation coverage, required direct-query index purposes, and exact migration text parity.
- Existing migration integration tests run SQLx migrations against PostgreSQL and inspect catalog data for representative required indexes.
- Story 4 Task 1 is schema-only. It must not fetch, parse, classify, or extract document files.

## Schema Design

Add `document_asset` as the canonical asset retrieval table:

- `id bigint generated by default as identity primary key`
- `document_source_category text not null`
- `document_source_id uuid not null`
- `asset_url text not null`
- `upstream_url text not null`
- `upstream_content_type text`
- `upstream_content_length bigint`
- `upstream_last_modified_at timestamptz`
- `retrieval_status text not null`
- `retrieval_error text`
- `retrieved_at timestamptz`
- `created_at timestamptz not null`
- `updated_at timestamptz not null`
- foreign key from `(document_source_category, document_source_id)` to `document(source_category, source_id)` with cascade delete
- unique constraint on `(document_source_category, document_source_id, asset_url)`

Use `asset_url` for the source URL to fetch and index. Keep `upstream_url` too so the raw upstream link is preserved even if future classification canonicalizes or redirects the fetch URL. On first implementation it can equal `asset_url`.

Add `document_content` as the extraction result and source-selection table:

- `id bigint generated by default as identity primary key`
- `document_asset_id bigint not null`
- `document_source_category text not null`
- `document_source_id uuid not null`
- `selected_source_url text not null`
- `selected_source_content_type text`
- `selected_source_content_length bigint`
- `official_source boolean not null`
- `source_rank integer not null`
- `extraction_status text not null`
- `validation_status text not null`
- `extraction_tool text not null`
- `extraction_tool_version text not null`
- `content_hash text not null`
- `extracted_text text`
- `extracted_html text`
- `extracted_at timestamptz not null`
- `created_at timestamptz not null`
- `updated_at timestamptz not null`
- foreign key from `document_asset_id` to `document_asset(id)` with cascade delete
- foreign key from `(document_source_category, document_source_id)` to `document(source_category, source_id)` with cascade delete
- check constraint requiring at least one of `extracted_text` or `extracted_html`
- unique constraint on `(document_asset_id, content_hash)`

Store `retrieval_status`, `extraction_status`, and `validation_status` as constrained `text` columns through `CHECK` constraints instead of PostgreSQL enum types. That keeps the existing table-spec renderer simple, keeps down migrations reversible without extra type drop ordering, and still gives the database explicit valid states.

Initial valid states:

- `retrieval_status`: `pending`, `fetched`, `not_found`, `unsupported_content_type`, `failed`
- `extraction_status`: `pending`, `extracted`, `empty`, `failed`
- `validation_status`: `unverified`, `valid`, `invalid`

## Indexes

Add generated indexes for:

- `document_asset(document_source_category, document_source_id)` as `AssetOwner`
- `document_asset(asset_url)` as `AssetUrl`
- `document_asset(upstream_url)` as `AssetUrl`
- `document_content(document_source_category, document_source_id)` as `DocumentContentOwner`
- `document_content(document_asset_id)` as `ForeignKeyPath`
- `document_content(official_source, source_rank)` as `OfficialContentSource`

The existing `document(source_category, source_id, content_type)` `AssetOwner` index remains useful for the current entity-table asset metadata and should not be removed during this task.
